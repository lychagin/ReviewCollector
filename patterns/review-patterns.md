## architecture

### p_002 · Дублирование логики в параллельных компонентах и сервисах
**Правило:** Идентичную логику в параллельных компонентах (appeals vs requests, create vs update) выноси в общий сервис, утилиту или базовый класс. Включает: блоки предзагрузки, методы маппинга, обработчики событий.
**Почему:** Дублирование приводит к рассинхронизации при изменениях — исправление в одном месте не распространяется на другие. Частый источник багов при параллельных сущностях.
**Встречалось:** 15 раз · **Приоритет:** high
**Пример:** "Блок предзагрузки данных (preloadLiftValidationDataPromise) дублируется 4 раза: appeals create, appeals update, requests create, requests update"

### p_010 · Имя поля в коде не совпадает с OpenAPI-контрактом
**Правило:** Имена полей в backend-коде, DGraph-схеме и OpenAPI-контракте должны быть идентичны. Любое расхождение (reportedByOrganization vs reportedByLegalEntity, workDescription vs workReason) ломает маппинг и клиентскую интеграцию.
**Почему:** Несоответствие имён обнаруживается поздно — при интеграционном тестировании или в продакшне. Следует проверять все новые поля на соответствие спецификации перед MR.
**Встречалось:** 9 раз · **Приоритет:** high
**Пример:** "Имя поля reportedByOrganization не совпадает с OpenAPI-контрактом, где используется reportedByLegalEntity. Вызовет расхождение при маппинге API → dgraph"

### p_022 · Использование сгенерированных валидаторов вместо ручных
**Правило:** Используй автоматически сгенерированные валидаторы из OpenAPI-спецификации вместо ручных DTO с дублированием правил валидации. Сгенерированные валидаторы всегда синхронизированы со спецификацией.
**Почему:** Ручные DTO с валидацией расходятся со спецификацией при её обновлении. Генерация из spec гарантирует единственный источник правды.
**Встречалось:** 8 раз · **Приоритет:** high
**Пример:** "Используется ручной DTO вместо сгенерированного из OpenAPI — при изменении спецификации нужно обновлять в двух местах"

### p_033 · Передача parentCtx для сохранения контекста авторизации и трейсинга
**Правило:** При вызове broker.call() внутри обработчиков всегда передавай { parentCtx: ctx }. Без parentCtx теряется контекст авторизации, tenant isolation и distributed tracing при вложенных вызовах сервисов.
**Почему:** Вызов без parentCtx делает вложенный вызов анонимным — права не проверяются в контексте текущего пользователя, трейс рвётся.
**Встречалось:** 3 раз · **Приоритет:** medium
**Пример:** "При загрузке из DGraph используется this.broker.call без parentCtx, в отличие от обновления, где передаётся { parentCtx: ctx }. Это приведёт к отсутствию контекста авторизации/трейсинга"

### p_035 · Несоответствие HTTP метода между спецификацией и реализацией
**Правило:** HTTP-метод endpoint должен быть одинаковым в OpenAPI спецификации, реализации контроллера и Postman-коллекции. Расхождение приводит к несовместимости клиентов и ложным ошибкам при автотестировании.
**Почему:** Postman-коллекция используется для ручного и автоматизированного тестирования. Расхождение метода означает неработающие тесты или неверную документацию.
**Встречалось:** 3 раз · **Приоритет:** medium
**Пример:** "Restore использует метод POST, но в Postman-коллекции указан метод PATCH. Нужно привести к единому HTTP-методу"

### p_036 · Мёртвый параметр API в спецификации без реализации
**Правило:** Не включай в OpenAPI-спецификацию параметры (expand, filter, sort) без реализации на бэкенде. Мёртвые параметры вводят клиентов в заблуждение и создают ложные ожидания функциональности.
**Почему:** Клиент, увидев параметр expand в спецификации, будет его использовать и не получит ожидаемого результата без каких-либо ошибок.

**Пример:** "Параметр expand описан в спецификации, но в backend-сервисе нет реализации expand. Мёртвый параметр в API вводит клиентов в заблуждение"

### p_040 · Moleculer: JournaledClientError vs MoleculerClientError
**Правило:** Для бизнес-ошибок (не найдено, нет доступа, невалидные данные) используй JournaledClientError вместо MoleculerClientError. JournaledClientError записывается в журнал и корректно обрабатывается middleware.
**Почему:** MoleculerClientError пропускает middleware журналирования. JournaledClientError обеспечивает трассировку бизнес-ошибок в журнале и корректные HTTP статусы.
**Встречалось:** 4 раз · **Приоритет:** medium
**Пример:** "Используется MoleculerClientError вместо JournaledClientError — бизнес-ошибка не попадёт в журнал"

### p_041 · Singleton-реестр Angular сервиса создаёт несколько экземпляров
**Правило:** Сервисы, предназначенные для singleton (кеш, реестр состояния), должны быть объявлены в providedIn: 'root', а не в providers модуля или компонента. Несколько экземпляров приводят к рассинхронизации состояния.
**Почему:** Angular создаёт отдельный экземпляр сервиса для каждого модуля, который его декларирует в providers. Два компонента получат разные кеши.
**Встречалось:** 3 раз · **Приоритет:** medium
**Пример:** "Сервис объявлен в providers модуля — будет создан новый экземпляр, а не singleton. Используй providedIn: 'root'"

### p_048 · Формат ответа не соответствует OpenAPI-схеме
**Правило:** Структура ответа должна точно соответствовать OpenAPI-схеме: правильная вложенность объектов, наличие всех required полей, корректные типы. Несоответствие ломает клиентов, ожидающих контракт.
**Почему:** Клиентский код генерируется из OpenAPI — если реальный ответ отличается, клиент получит null/undefined вместо данных.
**Встречалось:** 4 раз · **Приоритет:** medium
**Пример:** "Ответ возвращает плоский объект, хотя спецификация ожидает { data: {...}, meta: {...} }"

### p_056 · Несоответствие имён полей DGraph-схемы и OpenAPI
**Правило:** Имена предикатов DGraph должны точно совпадать с именами полей в OpenAPI-схеме. Расхождение требует дополнительного маппинга и является источником ошибок при рефакторинге.

**Встречалось:** 4 раз · **Приоритет:** medium
**Пример:** "DGraph предикат named reportDate, OpenAPI field — report_date: расхождение требует маппинга"

### p_058 · Компонент делает HTTP-запрос напрямую, минуя сервис
**Правило:** HTTP-запросы в Angular компонентах должны инкапсулироваться в сервисах. Компоненты не должны знать детали HTTP — они работают через сервисный слой.
**Почему:** Прямые HTTP запросы в компоненте нарушают SRP. Логика повторяется в нескольких компонентах вместо переиспользования сервиса.
**Встречалось:** 3 раз · **Приоритет:** medium
**Пример:** "HTTP запрос в компоненте напрямую через HttpClient — вынести в сервис"

### p_065 · Нарушение принципа единственной ответственности в методе
**Правило:** Метод, который выполняет несколько несвязанных операций (загрузка + обработка + отправка уведомления + логирование), нарушает SRP. Разбей на несколько методов с чёткой ответственностью.
**Почему:** Метод с несколькими ответственностями трудно тестировать изолированно. Изменение одной части требует понимания всего метода.
**Встречалось:** 3 раз · **Приоритет:** medium
**Пример:** "Метод processAndNotify делает слишком много: загружает, обрабатывает и отправляет уведомление — разбей на части"

### p_075 · Бизнес-логика в Angular шаблоне вместо компонента
**Правило:** Сложные выражения в шаблоне (тернарные с несколькими условиями, вызовы нескольких методов) переносить в вычисляемые свойства или computed signals компонента. Шаблон должен только отображать данные.
**Почему:** Бизнес-логика в шаблоне не тестируется unit-тестами. Сложные выражения замедляют change detection при каждой проверке.
**Встречалось:** 2 раз · **Приоритет:** low
**Пример:** "Сложный тернарный оператор в шаблоне — выносить в computed signal компонента"

### p_085 · Дублирование константных массивов вместо вынесения в shared
**Правило:** Константные массивы и объекты (списки статусов, маппинги) определяются в одном месте и импортируются везде, где нужны. Дублирование константных значений — источник рассинхронизации.
**Почему:** При изменении бизнес-логики нужно найти все копии. Одна константа в shared модуле гарантирует единственный источник правды.
**Встречалось:** 1 раз · **Приоритет:** low
**Пример:** "Массив статусов ['pending', 'active', 'closed'] дублируется в 3 файлах — выносить в shared constants"

## performance

### p_006 · Последовательные await в цикле вместо Promise.all
**Правило:** Не делай последовательные await в for..of цикле для независимых операций — это N-кратно замедляет выполнение. Используй Promise.all с map для параллельного выполнения независимых async-операций.
**Почему:** При 100 квартирах N последовательных запросов займут N×T времени вместо T с Promise.all. Частый паттерн при обходе вложенных сущностей.
**Встречалось:** 7 раз · **Приоритет:** high
**Пример:** "Последовательные await в цикле for..of вместо параллельного выполнения. Если квартир много, это будет медленно. Рассмотрите Promise.all с map"

### p_012 · Angular: вызов метода в шаблоне в цикле
**Правило:** Не вызывай методы компонента внутри @for или *ngFor в шаблоне — они вызываются при каждом цикле change detection. Используй computed signals, мемоизированные геттеры или prepare данные в компоненте.
**Почему:** Метод в шаблоне выполняется при каждом цикле change detection, включая mouse events. При 100 элементах это сотни лишних вычислений в секунду.
**Встречалось:** 5 раз · **Приоритет:** high
**Пример:** "Вызов getItemLabel(item) внутри @for — метод вызывается при каждом цикле change detection. Перенесите в computed signal или мемоизируйте"

### p_019 · take:0 загружает все записи вместо пустого результата
**Правило:** В DGraph take:0 означает 'без ограничения' (загрузить всё), а не 'вернуть 0 записей'. Перед передачей take в DQL-запрос проверяй take > 0 и используй условную логику или значение по умолчанию.
**Почему:** Если клиент передаёт take=0 (ожидая пустой результат), DGraph вернёт весь набор данных. Это неожиданное поведение, потенциально нагружающее базу.
**Встречалось:** 5 раз · **Приоритет:** high
**Пример:** "take: 0 в DGraph запросе означает 'без ограничения', а не 'вернуть 0'. Если limit=0, нужно возвращать [] без запроса к DGraph"

### p_054 · Отсутствие индекса DGraph для полей, используемых в фильтрах
**Правило:** Поля DGraph, используемые в предикатах фильтрации (has(), eq(), anyof()), должны иметь соответствующий индекс в схеме. Без индекса DGraph выполняет полный скан.
**Почему:** DGraph не может использовать eq() или anyof() без индекса — запрос либо упадёт с ошибкой, либо выполнится как full scan. Для строк нужен @index(term/exact), для чисел — @index(int).
**Встречалось:** 3 раз · **Приоритет:** medium
**Пример:** "Поле status используется в eq() фильтре, но не имеет @index(exact) в схеме"

## robustness

### p_003 · Отсутствие обработки ошибок: проглатывание и продолжение после ошибки
**Правило:** После вызова ErrorHandler.handle() всегда добавляй throw или return. Не используй пустой catch без реакции. В UI save-обработчиках оборачивай await mutateAsync() в try/catch. Парсинг user input (base64, JSON) тоже должен быть в try/catch.
**Почему:** Три связанных антипаттерна одной темы: выполнение после обработки ошибки продолжается в некорректном состоянии; пустой catch скрывает проблемы от пользователя; unhandled rejection в UI оставляет диалоги незакрытыми.
**Встречалось:** 14 раз · **Приоритет:** high
**Пример:** "После UnifiedErrorHandler.handle() в catch-блоке проверки дублей выполнение может продолжиться. Нужен явный throw или return после handle"

### p_004 · ?? вместо || при работе с пустыми строками
**Правило:** Используй || вместо ??, когда пустая строка должна считаться falsy. Оператор ?? срабатывает только на null/undefined — пустая строка '' через ?? не вызовет fallback. Критично для uid-полей: пустой uid молча передаётся как значение вместо fallback на текущее значение сущности.
**Почему:** Системная ошибка в 7+ местах кодовой базы. toUidString() может вернуть '', и тогда ?? не сработает — данные сущности перезаписываются пустым uid при update-операциях.
**Встречалось:** 10 раз · **Приоритет:** high
**Пример:** "Оператор ?? с toUidString некорректен: если toUidString(ctx.params.lift) вернёт '', то ?? НЕ сработает. Используйте || вместо ??"

### p_005 · Рекурсия загрузки данных без ограничения глубины
**Правило:** Рекурсивные функции загрузки данных должны иметь явный верхний лимит на количество итераций или общее число загруженных элементов. При превышении — возвращать ошибку или обрезать с предупреждением. Альтернатива: переписать на итеративный подход с while-циклом.
**Почему:** Без лимита рекурсивная загрузка может выполнить тысячи запросов к API при глубоких иерархиях, перегружая БД и сеть.
**Встречалось:** 6 раз · **Приоритет:** high
**Пример:** "рекурсивная функция loadPage загружает дочерние объекты страницами по 500, но не имеет ограничения на общее количество. Если у appeal тысячи requests, а у каждого — сотни tasks, количество запросов к v1.assets.getAll может быть огромным"

### p_009 · Отсутствие unsubscribe для RxJS подписок (Memory Leak)
**Правило:** Все RxJS подписки в Angular-компонентах должны быть отписаны при уничтожении компонента. Используй takeUntilDestroyed(), async pipe или Subject + takeUntil(this.destroy$) в ngOnDestroy.
**Почему:** Незакрытые подписки продолжают получать события после уничтожения компонента, вызывая утечки памяти и попытки обновить уничтоженное дерево.
**Встречалось:** 5 раз · **Приоритет:** high
**Пример:** "Отсутствие unsubscribe для подписок (Memory Leak) — подписки без cleanup в ngOnDestroy"

### p_011 · Angular @Input() в effect()/computed() не реактивен
**Правило:** Не читай @Input() напрямую внутри effect() или computed() — это не сигнал и не отслеживается реактивностью Angular Signals. Конвертируй @Input() в сигнал через input() или toSignal(), либо используй ngOnChanges.
**Почему:** effect() и computed() реагируют только на сигналы. @Input() — обычное поле; его изменение не перезапустит effect/computed, и компонент будет показывать устаревшие данные.
**Встречалось:** 6 раз · **Приоритет:** high
**Пример:** "В effect() читается this.someInput напрямую — @Input() не является сигналом. Используйте input() или toSignal()"

### p_013 · Все ошибки в catch маскируются как одна категория
**Правило:** Не используй catch-блок для маскировки всех ошибок под один код (404, 500). Различай типы ошибок: NotFound (404), ValidationError (400), NetworkError. Если ошибка не относится к ожидаемому типу — пробрасывай дальше через throw.
**Почему:** Маскировка всех ошибок как 404 скрывает реальные проблемы: ошибки соединения, внутренние ошибки сервиса. Клиент не может корректно реагировать на разные типы сбоев.
**Встречалось:** 8 раз · **Приоритет:** high
**Пример:** "Все ошибки в catch блоке возвращаются как 404 — даже ошибки соединения и внутренние ошибки сервиса"

### p_014 · Обработчик ошибок не останавливает выполнение
**Правило:** После вызова обработчика ошибок (ErrorHandler.handle, logger.error) добавляй return или throw. Без явной остановки код продолжает выполняться в некорректном состоянии после ошибки.
**Почему:** Код после ErrorHandler.handle() предполагает корректное состояние, которого нет. Продолжение выполнения может привести к повреждению данных или повторным ошибкам.
**Встречалось:** 6 раз · **Приоритет:** high
**Пример:** "После ErrorHandler.handle() в catch нет return/throw — выполнение продолжается после ошибки"

### p_015 · Под-операция молча не выполнена при ошибке
**Правило:** Если под-операция (отправка уведомления, создание связанной записи) завершилась с ошибкой, не проглатывай её молча. Либо пробрасывай ошибку, либо явно логируй с указанием контекста и продолжай с пометкой о частичном успехе.
**Почему:** Молчаливый провал под-операции создаёт иллюзию успеха — пользователь думает, что всё прошло, но нотификация не отправлена или связанная запись не создана.
**Встречалось:** 6 раз · **Приоритет:** high
**Пример:** "Ошибка отправки уведомления проглатывается — пользователь не узнает, что нотификация не была отправлена"

### p_020 · i18n ключ отсутствует в файле локализации
**Правило:** Каждый i18n ключ, используемый в шаблонах и компонентах, должен присутствовать во всех файлах локализации (ru.json, en.json). Отсутствующий ключ отображается как пустая строка или как сам ключ в UI.
**Почему:** Отсутствующий i18n ключ — молчаливая ошибка: пользователь видит пустое место или ключ вида 'module.component.label'. Не обнаруживается в runtime без проверки.
**Встречалось:** 5 раз · **Приоритет:** high
**Пример:** "Ключ 'appeals.form.status' используется в шаблоне, но отсутствует в ru.json"

### p_024 · DGraph datetime поле без атрибута index
**Правило:** Поля типа datetime в DGraph схеме должны иметь атрибут @index(hour) или @index(day). Без индекса сортировка и фильтрация по времени выполняются полным сканом — медленно при больших данных.
**Почему:** DGraph требует явного индекса для эффективных запросов с фильтрацией/сортировкой по datetime. Без индекса запрос выполняется полным сканом.
**Встречалось:** 4 раз · **Приоритет:** high
**Пример:** "Поле createdAt: datetime в DGraph схеме без @index(hour) — сортировка будет медленной на больших данных"
